An AI product needs more than a folder of PDFs. It needs the right manual, usable text and enough source context to tell where an answer came from. Manufacturer documents arrived as inconsistent scans, broken text, tables and conflicting product identifiers.

I designed, built and operated the processing and recovery systems that qualified this material for AI search, alongside acquisition and downstream handoff. The work combined economical extraction, layered AI classification, source-grounded identity checks and controlled publication.

The historical acquisition work reached 160 source collectors and 370,000 collected documents. A dated September 2026 status report recorded 110,000+ manuals in the production-clean catalog. Collected files, clean manuals, structured outputs and delivered backend records are different counts. The catalog total is not a claim that every manual was structured, indexed or delivered to the application.

Build a reusable acquisition layer

I built a shared collector runtime with deduplication, provenance, leases, retries and cost controls. It supported source collectors across manufacturer sites and public archives.

Content fingerprints prevented repeated discoveries from becoming duplicate processing. Source PDFs remained available for inspection and reprocessing, while run records connected collection failures to the work needed to resume them.

Acquisition supplied the source files. The eight-stage processing pipeline then inventoried, extracted, screened, classified, reconciled, structured, reported and published its outcomes. Targeted recovery and backend delivery used separate workflows.

The cloud operations case covers scheduling, monitoring and diagnosis for the collection fleet.

Operate the manuals platform on Azure

Azure Functions ran the collectors. The processing system used containerized batch execution on Azure, including Azure Container Instances and later Container Apps Jobs. PostgreSQL retained stage and campaign state; durable artifacts allowed an interrupted run to resume without treating missing local files as completed work.

I handled the operating problems that appeared at batch scale. PDF extraction ran in isolated subprocesses to release native memory, concurrency was bounded, and completed stages could be resumed rather than repeating paid processing. Run evidence identified the selected inputs, code and container version, outcomes and spend.

Azure Blob Storage retained sources and produced artifacts. Local PDF tools and Azure Document Intelligence supported the main extraction waterfall; targeted recovery also used richer document and vision processing where the failure required it.

Route extraction by document needs

I designed an extraction waterfall that tried local PDF tools before paid OCR or layout analysis. The decision depended on the quality of the extracted text. A scan and a readable text PDF did not need the same treatment.

Language-aware checks distinguished legitimate multilingual text from damaged extraction. This mattered because treating non-English text as corruption could trigger unnecessary processing while still failing to catch genuinely unreadable output.

A September 2026 production run processed 20,000 input documents for about $220 in variable processing cost, across clean, flagged and rejected outcomes. This is a dated run result, not a cost guarantee for every corpus or recovery campaign.

Decide which documents and identifiers to trust

Cheap initial screening preceded four layers of AI classification. The layers increased the available context, from initial pages to fuller document analysis and an agreement check. A checkpoint before deeper escalation allowed review of the batch and its processing needs.

Classification and identity were separate decisions. A document could be a useful manual while its model identifier remained uncertain. Reconciliation checked manufacturer, model, type and language against evidence in the document, using reviewed aliases and keeping unsupported identities flagged.

Filenames could supply tightly limited recovery evidence for missing fields; they could not override supported document contents. The goal was a reliable connection between a product and its manual, rather than a plausible-looking metadata record.

Build recovery around the failure cause

I built targeted recovery paths because failed documents did not share one cause. Readable text with missing headings needed structural repair. Corrupt extraction needed a return to the original PDF. Conflicting product metadata needed an identity check without repeating extraction.

Recovery selection retained the prior outcome, failure reason, source identity and existing artifacts. Trustworthy work could be reused. Preservation checks inspected structural changes, while unresolved cases remained available for review instead of being silently promoted.

Strengthen the release controls

I stopped a 5,000-document release after human review caught defects automated checks had missed, then added source-grounding and line-level preservation checks. Subsequent changes were qualified through staged batches of 250 to 5,000 documents.

This publication review was separate from the earlier classification checkpoint. Release evidence identified the exact candidate artifacts and approved membership. Publication retained original sources, distinguished accepted from unresolved outcomes and supported retry and inspection.

The important operating decision was to make a batch's completion and its readiness for release separately inspectable. A finished processing job did not, by itself, establish acceptable content quality.

Carry useful structure into retrieval

I prepared Markdown with useful headings and page references so downstream chunks could retain the relationship between a section, its text and its source. Unsafe heading candidates stayed in the body; page-bounded fallback sections provided a controlled alternative when a reliable semantic heading could not be recovered.

The handoff contract gave the backend one final enriched Markdown file per manual. Its chunking rules used section headings and carried page references as metadata. Internal quality sidecars remained processing evidence rather than an additional indexing dependency.

Backend delivery was a separate audited operation using an approved manifest and API verification. Publishing PDF, Markdown and metadata artifacts did not establish that every document was delivered or indexed. Lookup and serving connected product identity to documents, while this processing work supplied qualified, source-linked outputs for that handoff.

The separate memory evaluation measured retrieval on a different, explicitly scoped dataset. Its scores are not a quality score for this manuals corpus.
