Building a manuals platform for retrieval

All selected work
Problem
Turn inconsistent manufacturer PDFs into reliable, traceable knowledge for an AI assistant.
My contribution
Built 160 source collectors and owned the acquisition, extraction, recovery and retrieval-preparation workstreams.
Outcome
370,000 documents collected; 110,000+ structured Markdown documents prepared for downstream retrieval.

I built 160 source collectors, gathered 370,000 documents, and prepared 110,000+ structured Markdown documents for retrieval.

I owned acquisition, extraction and recovery. Classification and deduplication removed non-manual files, duplicates, service manuals and unrelated material from the retrieval corpus. The retained manuals became 110,000+ structured documents, with original files and source identity preserved for inspection and reprocessing.

Build a reusable acquisition layer

I built a shared collector runtime with deduplication, provenance, leases, retries and cost controls. That common layer supported 160 source collectors across manufacturer sites and public archives.

Content fingerprints prevented repeated discoveries from becoming duplicate work. Source PDFs remained available for inspection and reprocessing, while run records connected collection failures to the work needed to resume them.

The cloud operations case covers scheduling, monitoring and diagnosis for the running fleet.

Operate the manuals platform on Azure

Azure Functions ran the collectors, and Azure Blob Storage held source files and operating records. Python handled extraction and recovery. The processing layer called Azure Document Intelligence, Google Document AI and Gemini Vision where the document required them.

Route extraction by document needs

I designed an extraction waterfall that started with inexpensive local processing, assessed the output and escalated to OCR or richer document analysis when needed. Classification and content-grounded metadata guided the route.

Language-aware checks handled multilingual text, scans, tables, diagrams and technical symbols. This recovered useful content while avoiding unnecessary escalation to more expensive processing.

A September 2026 production run processed 20,000 input documents for about $220 in variable processing cost, across clean, flagged and rejected outcomes.

Build recovery around the failure cause

I created targeted recovery paths for corrupt files, incomplete OCR, mislabeled manuals and damaged tables. Each path retained the source, recorded the reason for recovery, resumed completed stages and bounded further processing cost.

When recovery changed a document's structure, preservation checks compared the output with its source. Review evidence supported a release decision for each changed batch.

Strengthen the release controls

I stopped a 5,000-document release after human review caught defects automated checks couldn't see, then added source-grounding and line-level preservation checks.

I qualified subsequent changes through staged batches of 250 to 5,000 documents. The resulting release process tied promotion to evidence of content quality, with headings, structure and provenance preserved for downstream retrieval.
