Give recurring work a common runtime.

Azure timer triggers start collection work within shared scheduling and cost controls.

Distinguish busy from broken.

A renewable blob lease prevents overlap. A busy lease produces a recorded skip, rather than another concurrent run.

Leave an inspectable record.

Each run records its identity, timestamps and outcome. Completed, skipped and failed work remain distinguishable.

Connect evidence to the next action.

Fleetwatch combines run records and coverage information with monitoring, cost controls and operating runbooks.

Conceptual operating flow. The busy-lease branch records a skip; it does not execute the collection.

I built the shared Azure Functions runtime, run records and Fleetwatch monitoring around a collection fleet. As the only cloud engineer, I also owned the platform's architecture, deployments and on-call.

The operating problem was broader than whether a timer fired: work could succeed, fail, be skipped to prevent overlap, or run out of useful source material. Operators needed to distinguish those states and know what to inspect next.

Control scheduled execution

Azure timer triggers started recurring work. Renewable blob leases prevented overlapping executions of the same collector, with a known lease conflict recorded as a skip rather than treated as a collection failure.

I kept the scheduling design tied to concurrency, overlap, retries and cost. The shared runtime supported 160 source collectors without introducing a separate scheduler before the operating requirements justified it.

Make each run inspectable

I added run records carrying source identity, timestamps, outcome and available collection or cost metrics. Individual JSON artifacts in Azure Blob Storage gave operators an inspectable record alongside application logs.

Fleetwatch combined a dashboard, snapshot API and alerts to connect execution outcomes with fleet health and coverage. Deployment preflight checks, rate limits and per-service cost tracking made operating controls part of the platform.

The useful distinction was between a failed collection, intentionally skipped work and misleading monitoring. A single alert count could not explain those states.

Resolve the root cause behind the alerts

On 24 August 2026, correcting stale coverage counts and alert logic reduced the attention list from 14 sources to 1, a measure of sources needing manual review rather than incidents or downtime.

Carry the operating knowledge forward

Monitoring, preflight checks, cost controls and runbooks connected the runtime to the people maintaining it. I worked to make the platform diagnosable by another operator, with records that linked symptoms to the relevant execution and source.

This operating layer supported the document intelligence platform. The cloud foundation case covers environment setup, infrastructure as code, access management, migrations and production recovery.
