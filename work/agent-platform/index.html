Carry the task beyond a chat reply

A useful assistant has to do more than answer a message. At eeva, someone could upload a document, ask about an appliance and continue into a service task. The engineering challenge was keeping the relevant information and the person's choices attached as that task moved between conversations, agents and tools.

I co-led the platform with one other engineer. Seven capabilities I personally built were adopted by the production team and shipped: work spanning scanning and document ingestion, manual-grounded answers, message storage and vectorisation, calling and repair flows. The platform as a whole was a team effort.

Keep the task intact across specialist agents

The Google ADK orchestrator routed requests to 16 specialist agents. FastAPI services gave them tools for product records, documents, providers and service workflows. I co-led this runtime and connected it to the services I owned.

The important distinction was between what an agent understood and what the application retained. Account and session context identified the conversation. Product records identified the appliance and provider. Workflow state preserved the current task and the person's selection, so a follow-up did not have to start from scratch.

An agent's suggestion was not itself an instruction to place a call. The service journey needed a separate review of the proposed action. The opening interaction illustrates that boundary; it does not call a provider or book an appointment.

Keep memory current without losing history

I was the primary engineer on the standalone memory service, separating long-term context from the agent runtime. PostgreSQL and pgvector supported structured facts, semantic retrieval, entities and relationships that could change over time.

Remembering more text was not enough. If a person explicitly changed their preferred provider, the service needed to retrieve the new preference without erasing the earlier record or changing which appliance they owned. My work covered contradiction detection, fact versioning, expiry, category filtering and selective writes, alongside hybrid retrieval.

A one-off provider selection and an instruction to remember a new preference are different inputs. The example below uses an explicit preference update. Conversation history, active workflow state and long-term memory serve different purposes.

Measure which context comes back

I built the memory retrieval evaluation harness to compare four representations and model configurations. The 10 April 2026 internal experiment used 303 facts and 729 queries, including adversarial cases. OpenAI + Markdown led Recall@1; Google + JSON led Recall@3. The choice depended on whether the consuming workflow needed its first result or a shortlist.

Category reports also exposed weaknesses that an overall score could hide. These results describe that dated experiment, not a validation of every later implementation of the memory service. The detailed case retains the complete benchmark tables.

Read uploads before the agent answers

Process the upload before asking the agent to reason about it. I built scanning, document-ingestion and manual-grounded answer capabilities. The product upload path classified the document, selected a suitable extractor and supplied extracted fields to the agent alongside the question.

The implementation used Google Cloud Document AI for supported document types, Azure Document Intelligence for contracts, business cards and identity documents, and Gemini Vision for inputs such as appliance labels. Original uploads and extraction metadata could be retained with account context, rather than leaving only a generated answer.

That gave the conversation concrete information to work with: which document was uploaded and what it said. It was a different workflow from the eight-stage manuals platform, which acquired and prepared the reference collection used for search.

Connect voice, WhatsApp and LINE

I owned voice and messaging integrations across Vapi, Twilio and ElevenLabs, with WebSocket and SSE streaming, as well as WhatsApp and LINE entry points. Voice involved moving live audio between the caller and model, providing conversation context, recording both sides of the exchange and cleaning up the connection when it ended.

Messaging needed more than plain text. The LINE implementation included provider cards with click-to-call details, appointment-ticket summaries and calendar choices. These interfaces let a person inspect options and confirm a selection. They did not make every incoming message an authorised external action.

The broader platform combined my integration work with team-built workflow and safety components. I contributed calling and repair capabilities; the full workflow, persistence and guardrails should be understood as shared platform work. The selected provider and decision needed to remain attached to the task as it progressed.

Reuse backend tools through APIs and MCP

Reuse product operations instead of rebuilding them for each client. The platform exposed backend operations for records, documents and service tasks through APIs. I built and deployed two MCP servers on Google Cloud Run, making existing backend tools available to additional agent clients through typed interfaces.

The MCP deployments were an integration branch, not a replacement for the web, voice and messaging paths. Their purpose was to reuse the product's capabilities through another interface. My broader integration work also included Home Assistant device controls.

That connected product engineering to deployment and operation of the supporting services. The cloud foundation case covers my environment, delivery and recovery responsibilities.
