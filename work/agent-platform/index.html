At eeva, I co-led an AI product platform with one other engineer. My work connected document-grounded answers, persistent context and service workflows, with seven personally built capabilities adopted by the production team and shipped.

I was the primary engineer on the standalone memory service, owned voice and messaging integrations, and built and deployed two MCP servers on Google Cloud Run. The wider platform was a team effort.

Ship capabilities across the product journey

The product needed to carry a request beyond a single response. A person could provide a document, ask about an appliance, retrieve relevant information and continue into a service workflow with the context intact.

My shipped capabilities connected three parts of that journey:

  • Document intelligence: scanning, document ingestion and answers grounded in source manuals.
  • Persistent context: message storage and vectorisation, carrying useful information across conversations.
  • Service workflows: calling and repair flows that preserve the person's choices and require approval before external actions.

Coordinate specialists with typed tools

I co-led the Google ADK runtime, with an orchestrator routing work to 16 specialist agents. FastAPI services connected the runtime to typed tools for product records, retrieval and service workflows.

The architectural constraint was continuity: account scope, session context and workflow state needed to remain attached as different agents and tools handled the task. A follow-up request could then use the appliance, provider or decision already established in the conversation.

Typed inputs and scoped credentials made permissions enforceable in software. They did not depend only on an instruction in a prompt.

Build persistent, relationship-aware memory

As primary memory-service engineer, I worked on memory as its own deployable service. PostgreSQL and pgvector combined structured facts and semantic retrieval with entities and time-dependent relationships.

A stored fact is not always a current fact. My work included contradiction detection, fact versioning, expiry, category filtering and selective writes, so new information could change the relevant context while retaining useful history. Hybrid retrieval connected that context to the task at hand.

Separating memory from the agent runtime gave context handling a clear service boundary. Product workflows could use the same memory capabilities without treating a conversation transcript as the entire system of record.

I also authored the memory retrieval evaluation harness. In its 10 April 2026 internal experiment, OpenAI + Markdown reached 93.8% Recall@3 and 0.878 MRR@3 across 303 facts and 729 queries. This is evidence for that configuration and experiment, rather than a score for every subsequent version of the memory service.

The comparison mattered more than one headline score: OpenAI + Markdown led Recall@1, while Google + JSON led Recall@3. Category reports exposed weaknesses hidden by the aggregate, helping make representation and ranking choices explicit.

Connect household records and document intelligence

The product's PostgreSQL records connected accounts, homes and assets, documents, providers, maintenance activity and conversations. Product tools could carry a selection or recommendation into persistent workflow state.

I built scanning and document-ingestion capabilities and manual-grounded answers. The wider product upload flow used document-AI services to extract fields and retained original uploads alongside metadata for account-scoped retrieval. That upload flow complemented the separate appliance document platform, which acquired and prepared the reference corpus.

Own voice, messaging and service execution

I owned the voice and messaging integrations using Vapi, Twilio and ElevenLabs, with WebSocket and SSE streaming. Those entry points connected requests and confirmations to shared context and product workflows.

The repair workflow made the execution boundary concrete:

  1. Identify the problem and relevant appliance.
  2. Retrieve warranty, ownership and document context.
  3. Find providers and preserve the person's selection.
  4. Present the proposed action for explicit approval.
  5. Carry the authorised call or scheduling action through and record its outcome.

I built the approval controls, typed inputs, account scoping, duplicate-action prevention and decision audit records. Persisted state preserved the selection and consent, rather than asking an agent to reconstruct them from a conversation. The interactive illustration above shows that boundary using example content.

Extend the platform through integrations

I built and deployed two MCP servers on Google Cloud Run to expose existing backend tools to other agent clients through typed interfaces. My voice and messaging work also connected channels and Home Assistant device controls to the product.

The broader platform combined web, uploads, chat, voice and API entry points. My ownership connected implementation with deployment and operation of the supporting services. The cloud foundation case covers that delivery responsibility.
