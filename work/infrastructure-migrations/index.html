Problem: Shipping an AI product also meant providing environments, access, deployment paths and operational support as its services and database platforms evolved.

My contribution: As the only cloud engineer at eeva, I owned cloud architecture, deployments and on-call. My work spanned Azure and Google Cloud, infrastructure as code, identity, private connectivity, migrations and incident recovery.

Outcome: I created staging, modernised development and production environments, delivered infrastructure with Terraform and Bicep through GitHub Actions, and turned production incidents into monitoring rules and runbooks.

Establish the environments behind delivery

I created the staging environment and modernised development and production. This work sat alongside the application itself: developers needed somewhere to test changes, a way to deploy them, and an environment whose configuration could be understood and maintained.

Terraform and Bicep captured infrastructure as code, with GitHub Actions supporting delivery. My responsibility included the cloud setup and the operating work after deployment, across Azure and Google Cloud.

Connect services with appropriate access

I managed IAM, Key Vault and private service connections. Identity, secrets and connectivity were part of making the product's services work together while keeping access scoped to their responsibilities.

I also owned Canadian data-residency compliance. Residency was a constraint on the cloud work, alongside the requirements of the services using those environments.

Evolve the database and hosting platforms

My work included database migrations to GCP and Neon, as well as deploying two MCP servers on Google Cloud Run. Those servers exposed existing platform tools through a common interface; the agent-platform case explains that integration.

The architecture overview groups my cloud responsibilities across services and environments.

Recover the system and retain the learning

I led recovery of a failed production database migration. In a separate incident, I worked with Microsoft support to resolve an Azure Traffic Manager and App Service failover fault.

Both incidents became monitoring rules and runbooks. Recovery included leaving the next operator with a way to recognise and respond to the problem.

Own the operating responsibility

I owned architecture, deployments and on-call for the collection platform and built 160 source collectors. Run ledgers, dashboards, alerting, deployment preflight checks and per-service cost tracking supported that work.

The cloud-operations case goes deeper into one part of that responsibility: scheduling, overlap controls and root-cause work that reduced sources needing manual attention from 14 to 1.
